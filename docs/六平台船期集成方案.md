# 六平台船期查询集成系统 —— 整体实施方案

> 历史设计资料，部分入口与阶段判断已被后续实现替代；不是当前部署说明。上线流程以 DEPLOYMENT.md 和实际提供商代码为准。

> 目标：把 COSCO / MAERSK / HAPAG / CMA / MSC / OOCL 六大船司的船期查询统一接入 OceanScope，形成「一次输入，六平台并表」的集成船期查询。本文基于已完成的前端摸底（6 平台船期结果接口）、数据库总表（1031×38）代码字段验证、以及 OceanScope 现有架构评估。

---

## 1. 目标与范围

- **业务目标**：用户在统一界面选「起运港 → 目的港 → 日期」，一次拿到六大船司的船期并表（船名/航次/起止时间/中转/服务模式/直达链接），支持筛选、对比、排序。
- **一期范围**（最稳、免登录 API 可直连）：COSCO + MAERSK。
- **二期范围**（需登录/SSR）：HAPAG（免登录子集）+ CMA（浏览器抓 SSR）。
- **三期范围**（接口待摸底确认）：MSC + OOCL。
- **不纳入**：运费、订舱（OceanScope 已有独立模块，互不耦合）。

## 2. 现状盘点（摸底结论）

### 2.1 六平台船期结果接口

| 平台 | 船期结果接口 | 结果形态 | 港口输入字段 |
|---|---|---|---|
| COSCO | `elines.coscoshipping.com/ebschedule/public/purpoShipmentWs` + `getDelayPorts` | 逐班（船名/航次/开到达/服务模式 CY-DOOR） | 城市代码 + 城市Uuid |
| MAERSK | `api.maersk.com/routing-unified/routing/routings-queries` + `deadlines/queries` | 逐班（船名航次/时间/Deadlines） | RKST 代码 + Geo ID(from/to) |
| HAPAG | `schedule.api.hlag.cloud/api/routes` | 逐班 | LOCODE（startLocation/endLocation） |
| CMA | `ebusiness/schedules/routing-finder`（SSR 页面） | 服务级方案（EXX/MTE/HBB）+ POL码头/日期 | LOCODE + Port/Ramp/Door 类型 |
| MSC | 港口全集 `GetAllAvailableCountriesAndPorts`；Search 触发 `SearchVessels` | 结果接口未定位 | 国家+港口全集 |
| OOCL | 港口 `AutoCompleteSailingSchedule` | 结果接口未触发确认 | UNLocode + Internal Code |

### 2.2 免登录可抓性

| 平台 | 免登录 |
|---|---|
| MAERSK | ✅ 浏览器会话免登录可查 |

| CMA | ✅ 免登录（SSR 页） |

| MSC / OOCL | ⚠️ 船期结果接口待进一步确认 |

### 2.3 港口标识字段验证（总表可复用性 —— 已实测）

| 平台 | 船期接口要的 | 总表对应列 | 实测结果 |
|---|---|---|---|
| MAERSK | URL `from/to` 参数 | `Maersk Geo ID` | ✅ 上海 `2IW9P6J7XAW72`、洛杉矶 `2LMUYHDQXMRNJ` 与船期 URL **完全一致** |
| MAERSK | `fromRkstCode/toRkstCode` | `Maersk RKST 代码` | ✅ 上海 CNSGH、洛杉矶 USLSA、鹿特丹 NLROT |
| COSCO | 船期城市代码 | `COSCO 船司港口码` | ✅ 上海 CNSHA、洛杉矶 USLSA、新加坡 SGSGP |

**核心结论**：总表的**代码字段（GeoID/RKST/城市ID/船司港口码/LOCODE）全部可用于船期集成，已实测对得上**。页面显示文本（地点名称/显示地址）仅作命中核对与溯源，**不进船期数据流，不一致不影响**。

## 3. 总体架构

```
┌─────────────────────────────────────────────────────────────┐
│                    前端（/schedules 改造）                     │
│   PortAutocomplete(统一港口搜索) → 日期 → 六平台 tab / 并表     │
└──────────────────────┬──────────────────────────────────────┘
                       │ POST /api/schedules/query {origin,dest,date}
┌──────────────────────▼──────────────────────────────────────┐
│              BFF 聚合层（Next.js API Route）                   │
│  1. 解析起/目的 → 从主数据取六平台各自代码                      │
│  2. 并行调各平台 Provider（Promise.allSettled，单平台失败不影响其他）│
│  3. 归一化为统一 SailingSchedule[]，标注 platform+source       │
│  4. 命中缓存优先；失败回退最近入库数据                          │
└───────┬──────────┬──────────┬──────────┬──────────┬─────────┘
        ▼          ▼          ▼          ▼          ▼
   COSCO      MAERSK     HAPAG      CMA       MSC/OOCL
  Provider   Provider   Provider   Provider   Provider
   API直连    API直连   API(需登录)  SSR浏览器   浏览器
└──────────────────────┬──────────────────────────────────────┘
                       ▼
             SailingSchedule 表（归一化入库）
```

## 4. 数据层设计（数据库改动）

### 4.1 schema 改动点（小幅，不推翻）

| 位置 | 改动 | 原因 |
|---|---|---|
| `CarrierPortMapping` | **加 `codeType` 字段**（String），`@@unique([carrierId, portId, codeType])` | 一平台多代码：MAERSK(GeoID/RKST)、COSCO(城市ID/船司港口码)、MSC(港口ID/系统LOCODE)、OOCL(地点ID) |
| `Port` | **加 `source` 可空字段**（String?） | 对应总表「资料来源」(WPI/SMDG/UNLOCODE) |
| `Port.region` | 从 country 推导填默认值，或改 `String?` | 总表无 region |
| `Carrier` | 无需改，seed 6 家 | — |
| `SailingSchedule` | **加 `granularity` 枚举**（VESSEL=逐班 / SERVICE=服务方案） | CMA 返回服务级方案，COSCO/MAERSK 返回逐班 |

### 4.2 港口主数据导入（总表 → 长表）

1 行总表 → 1 条 `Port` + N 条 `CarrierPortMapping`：

- `Port`：`name`=港口英文名、`nameZh`=中文名、`locode`=UN/LOCODE（唯一键）、`country`、`countryCode`、`region`=推导、`source`=资料来源
- `CarrierPortMapping`（每平台按其列生成 codeType 条目）：
  - MAERSK → (GeoID, codeType=GEOID)、(RKST, codeType=RKST)
  - COSCO → (城市ID, codeType=CITY_UUID)、(船司港口码, codeType=CITY_CODE)
  - HAPAG → (业务LOCODE, codeType=LOCODE)
  - CMA → (LOCODE, codeType=LOCODE)
  - MSC → (港口ID, codeType=PORT_ID)、(系统LOCODE, codeType=LOCODE)
  - OOCL → (地点ID, codeType=LOCATION_ID)

写脚本 `scripts/import-ports.ts`（Prisma upsert），幂等可重复执行。

### 4.3 COSCO 城市 ID 还原（前置）

`COSCO 城市 ID` 列当前是科学计数法（如 `7.38873E+14`），真实值是被 `id=(\d+)` 的长数字 Uuid。**需先从抓取接口记录还原成纯长数字**，否则船期接口拿到科学计数法字符串会失效。还原口径：从各平台验证截图/记录里的 `id=(\d+)` 取原始 15 位数字，覆盖科学计数法值。还原后 `COSCO 城市 ID` 才是船期城市 Uuid。

> 该还原为独立前置任务，不影响其他平台。

## 5. 抓取层设计（Provider/Adapter 模式）

把现有 `cosco-scraper` 抽成通用 Provider 框架，新增平台只加一个文件 + 一个映射，不动前端。

### 5.1 统一接口定义

```ts
// src/features/schedules/server/providers/types.ts
interface ScheduleProvider {
  id: "COSCO" | "MAERSK" | "HAPAG" | "CMA" | "MSC" | "OOCL";
  granularity: "VESSEL" | "SERVICE";
  requiresAuth: boolean;
  fetch(criteria: {
    origin: { code: string; locode: string };   // 各平台自身代码
    dest: { code: string; locode: string };
    date: string;                                 // YYYY-MM-DD
    weeks?: number;
  }, ctx: ProviderCtx): Promise<RawSchedule[]>;
}
// ProviderCtx 携带：session/登录态、fetch工具、超时、network记录
```

### 5.2 各平台 Provider 实现方案

| 平台 | 抓取方式 | 关键参数来源 | 特殊处理 |
|---|---|---|---|
| **COSCO** | API 直连 `purpoShipmentWs`（复用现有双模式，迁入框架） | 城市Uuid + 城市代码 | 已有 API+浏览器双模式、缓存、锁，直接泛化 |
| **MAERSK** | API 直连 `routing-unified/routing/routings-queries` + `deadlines/queries` | `from/to`=GeoID、`fromRkstCode/toRkstCode`=RKST、`fromServiceMode/toServiceMode`=CY | 一期新写；header/Referer 参照 COSCO 方式建立会话 |
| **HAPAG** | API `schedule.api.hlag.cloud/api/routes`（需登录态） | startLocation/endLocation=LOCODE、startHaulage/endHaulage、containerType | 免登录直连 401 → 需带登录 session/token；港口搜索 locations 接口免登录可先做 |
| **CMA** | Playwright 抓 `routing-finder` SSR 页 | GetAllPlaces 拿 LOCODE+Port/Ramp/Door | 结果是**服务级方案**非逐班，落 `granularity=SERVICE`；需过滤 Port 类型（排除 Ramp/Door） |
| **MSC** | 浏览器（结果接口待确认） | 港口全集 GetAllAvailableCountriesAndPorts | 需先摸底 Search 后的结果列表接口 |
| **OOCL** | 浏览器（结果接口待确认） | AutoCompleteSailingSchedule | 需先摸底 Search 后的结果接口 |

### 5.3 登录态管理（HAPAG）

- 免登录只能拿部分/需登录完整船期，页面明确提示。
- 方案：后端维护 HAPAG 登录会话（浏览器抓取时复用登录 Cookie），或限制免登录粒度并在结果标注「需登录看完整可用性」。
- 具体登录方式在二期实现前用一次浏览器实测确认（token 来源、失效时长）。

## 6. 统一数据模型与字段归一化

归一化后的 `SailingSchedule` 字段（扩展现有模型）：

| 字段 | 说明 | COSCO | MAERSK | HAPAG | CMA |
|---|---|---|---|---|---|
| carrier | 船司 | ✓ | ✓ | ✓ | ✓ |
| granularity | VESSEL/SERVICE | VESSEL | VESSEL | VESSEL | SERVICE |
| vesselName / voyage | 船名/航次 | ✓ | ✓ | ✓ | —（服务名） |
| serviceName | 服务名(EXX等) | ✓(航线) | ✓ | ✓ | ✓ |
| originPort / destinationPort | 起/目的港 | ✓ | ✓ | ✓ | ✓ |
| etd / eta | 开/到达时间 | ✓ | ✓ | ✓ | 日期+方案 |
| transitTime | 在途天数 | ✓ | ✓ | ✓ | ✓ |
| direct | 直达/中转 | ✓ | ✓ | ✓ | ✓ |
| originService / destService | 起运/目的服务模式 CY/DOOR | ✓ | ✓ | — | — |
| terminal / portCutoff | 码头/截关 | ✓ | ✓ | ✓ | ✓(POL码头) |
| transitPorts | 中转港 | ✓ | ✓ | ✓ | — |
| source | COSCO_LIVE_QUERY / MAERSK_LIVE_QUERY / ... | ✓ | ✓ | ✓ | ✓ |

**对齐口径**：所有平台统一落 `etd/eta`（Date）、`transitTime`（天）、`direct`（bool），服务模式统一为 CY / DOOR / SD。展示层只用归一化字段，平台原始显示文本仅存溯源。

## 7. 调度与缓存策略

- **实时**：用户查询时 BFF 并行调各平台 Provider（`Promise.allSettled`，单平台失败不影响其余），结果并入 `scheduleStorage` 缓存。
- **定时预取**：热门 O-D 对（如上海→洛杉矶、上海→新加坡…Top N）用 cron 定时抓取入库，冷门实时抓。
- **降级**：实时抓取失败 → 回退最近一次入库数据（标注 source=CACHE + 抓取时间）；某平台挂 → 其余平台照常并标记。
- **去重/锁定**：复用现有 `cosco-scraper-lock`，按 (carrier, origin, dest, date, week) 做查询锁，避免并发重复抓。
- **封禁规避**：每平台限速（如单平台 ≥ 3s/次）、失败退避、浏览器模式复用现有 session。

## 8. 前端集成

- 改造 `/schedules`：`PortAutocomplete` 已查统一主数据 → 选中即得六平台代码，无需感知平台。
- 结果页：六平台 tab 切换 + 「全部并表」视图；每行标注平台徽标、granularity（逐班/服务方案）、直达链接（跳转各平台船期页，MAERSK 可拼 pointToPoint URL，其余见 `六大船公司船期查询直达链接.md`）。
- 支持筛选（船司/直达/时间窗）、排序（最早出发/最快中转/最早到达）、对比（复用 ScheduleCompare）。

- 每平台用已知港口（上海→洛杉矶）做基准测试，比对船期字段与平台页面人工核对。

## 11. 风险与待确认项

| 项 | 说明 | 处置 |
|---|---|---|
| **MAERSK 登录** | 船期结果接口浏览器会话免登录，但直连 API 是否需鉴权待实测 | 一期实现前用一次 API 直连测试确认 header/Referer |
| **HAPAG 完整船期需登录** | routes 免登录 401，页面明确提示 | 二期做登录态管理；一期先做免登录子集 + 标注 |
| **CMA 为服务级方案** | 非逐班，字段模型需 `granularity=SERVICE` | 已在统一模型覆盖 |
| **MSC / OOCL 结果接口** | 浏览器会话未触发确认 | 三期前用一次浏览器摸底补全 |
| **COSCO 城市ID 科学计数法** | 需还原，否则船期接口失效 | 独立前置任务 |
| **港口英文名取哪个** | 多平台英文名不一 | 定标准：以 UN/LOCODE 官方名或 MAERSK 完整地点名为主 |
